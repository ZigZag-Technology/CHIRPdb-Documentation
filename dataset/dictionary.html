Data dictionary for the CHIRPdb database prepared for the Alan Turing Institute Data Study Group. See the dataset overview for context, provenance and limitations. Content conventions follow DAMA-DMBOK.

What the database contains

This dictionary documents the full CHIRPdb schema. The database as delivered is populated end to end: every pipeline stage has run over the whole corpus. Expect data in:

  • Reports & text - documents, authors, sentences, and the report-derived incident facts in document_particulars and document_vessels. Two corpora sit here, separated by documents.jurisdiction: 796 UK MAIB reports ('UK') and 456 US NTSB reports ('US'), 1,252 documents in total.
  • Incident metadata from the MAIB spreadsheets - occurrences (9,063), vessels (9,830), affected_persons (3,040), affected_persons_ppe (924), the report↔occurrence link carried on documents.occurrence_id, plus the vocabularies feeding them (taxonomy_terms, 410 terms across eight trees; ppe_items, 9). MAIB-only: NTSB publishes no equivalent dataset, so these tables describe UK incidents alone and no NTSB document carries an occurrence_id. This is much the larger incident record, and it is nearly disjoint from the report corpus - only 58 reports link to an occurrence (see documents).
  • Findings from the record pass - safety_issues (11,254, of which 479 are record_type = 'safety_lesson'), recommendations (4,127), the recommendation_organisations links (3,658; 3,342 MAIB / 316 NTSB) and the organisations they resolve to (802). Every document has been through the pass: documents.records_pass_at is set on all 1,252.
  • Passages - passages (15,381; 13,892 MAIB / 1,489 NTSB) and passage_sentences (15,939; 14,382 / 1,557), written by the record pass, one passage per record: the sentences a safety issue or recommendation was read from, so every record carries its own provenance. No general passage pass has run, so these hold record passages and nothing else.
  • Narrative entities - narrative_entities (545,649) and narrative_entity_mentions (1,267,349): one entity per distinct thing per document, with every in-text mention resolved to it and located by character span.
  • Embeddings - passage_embeddings carries a vector for all 15,381 passages under the active model, shield_code_embeddings all 452 code × strategy vectors, and passage_embedding_queue is drained (0 rows). See § 5.
  • Seeded reference vocabularies - shield_layers / shield_code_categories / shield_codes (the full SHIELD taxonomy), narrative_entity_types (14 types, referenced by every entity row), taxonomy_terms and ppe_items. embedding_models and embedding_strategies are seeded on the same footing - they configure the embedding layer rather than describe incidents.

Five tables are empty as delivered:

  • passage_shield_codes - the one analytical link the database is missing. The taxonomy is loaded and every passage is embedded, but no code has been attached to any passage. See the table's own section for what the embedding layer offers in its place.
  • analysis - a spare table for a future per-passage pass. Nothing writes it.
  • legislation and safety_issue_legislation - the legislation-attachment feature is not implemented.
  • author_identifiers - nothing populates it at this stage.

Some columns of otherwise-populated tables are empty too, and they are flagged where they appear. The ones most likely to be reached for: sentences.relevance_score; every contact field on organisations and authors; safety_issues.name and recommendations.action (the analyst-authored summaries - the report's own wording is in the passage, not here); and every is_verified / verified_at pair.

How to read this document

Every column is classified in the Source column as one of:

LabelMeaning
SourceSource-document field - value taken from the source report, MAIB or NTSB (PDF content or file metadata)
MAIBMAIB Data Portal field - value taken from the MAIB spreadsheet extract. Used only on the spreadsheet-fed tables, which hold UK incidents alone
PipelinePipeline-derived (deterministic) - computed by the ingestion pipeline with no model involvement
AI-UAI-generated (unverified) - produced by an LLM or NLP model, not confirmed by a human
AI-VAI-generated (human-verified) - AI-produced and confirmed by an analyst
SystemSystem metadata - surrogate keys, timestamps, status flags, generated search columns, seeded reference data
AnalystAuthored by a person in the review surface - never produced by the pipeline or a model, and empty until someone fills it in

A slashed label (Pipeline / AI-U) marks a column whose extractor is deterministic with a model fallback.

Four conventions apply throughout:

  1. Row-level verification. Tables carrying an is_verified flag (passage_shield_codes, safety_issues, recommendations) hold AI-generated content whose verification status varies per row. Their content columns are marked AI-U (or Pipeline / AI-U where a deterministic extractor populates them today); treat rows where is_verified = true as AI-V. Sentences are the analogous case at document level: documents.status = 'verified' marks a document whose extracted text an analyst has confirmed.

    In this delivery, nothing has been verified. No row anywhere carries is_verified = true, no document is at status = 'verified', and the Analyst columns (safety_issues.name, recommendations.action) are empty. The AI-V and Analyst labels below therefore describe what a column would hold after review, not what it holds now - read every AI-U column as machine output no human has checked.

  2. Sentence text. Text is extracted by a vision LLM reading a rendered image of each page, with deterministic passes (structural-metadata normalisation, line rejoin, content-loss repair) applied on top of the model output. Sentence text and structure columns are therefore marked AI-U, qualified by the parent document's status.
  3. Two record sets, linked - not merged. Incident data comes from two sources kept in separate tables rather than reconciled into one row:
    • the MAIB Data Portal spreadsheet → occurrences and its children vessels / affected_persons, plus the vocabularies taxonomy_terms / ppe_items. Spreadsheet-only facts, UK-only; source_id / source_modified_at carry MAIB's per-record identifier and revision date, driving upsert on each refresh so only MAIB-revised rows are touched. Columns on these tables carry the MAIB label.
    • the report PDF, MAIB or NTSB → document_particulars (incident facts stated in the report) and document_vessels (vessels named in the report), each hanging off documents. Columns fed this way carry the Source label, which says nothing about which body published the report - read documents.jurisdiction for that.

    A MAIB report links to its occurrence through documents.occurrence_id, with documents.occurrence_matched_on recording how the link was made (publication_number or manual); several reports can point at the same occurrence (e.g. an interim report followed by the final one). NTSB documents have no occurrence to link to, so only the report-PDF set applies to them.

  4. Jurisdiction split. documents.jurisdiction is the column that separates the corpora - 'UK' for MAIB, 'US' for NTSB - and everything owned by a document (sentences, document_particulars, document_vessels, passages, safety_issues, recommendations, narrative_entities) inherits that split through its document_id. Field coverage differs between the two: see the per-column notes on documents, document_particulars and document_vessels, and the fill-rate figures in the README.

All tables carry created_at and updated_at (timestamptz, defaulting to now(), with updated_at maintained by a BEFORE UPDATE trigger). These are listed once per table without repeating the explanation.

Document status lifecycle: queued → extracting → extracted → verified, with extracting → extraction_failed on an irrecoverable crash. extracted means the automated pipeline finished; verified means an analyst confirmed the results. The claim_* columns are the extraction lease used to recover documents stranded by a crashed worker. As delivered, all 1,252 documents are at extracted, and 201 carry extraction_fallback = true (182 MAIB, 19 NTSB).

The records_* columns track the separate record pass. As delivered every document has records_pass_at set - the pass has run over the whole corpus - and 981 carry records_fallback = true, meaning the deterministic extractor alone did not settle the result and an LLM route was used. That flag says how the records were reached, not whether they are wrong.

The report corpus and the spreadsheet barely overlap, and that is the database's sharpest limit. occurrence_id links only 58 reports to an occurrence. The cause is on the spreadsheet side: it only goes as far back as 2018. Since then, MAIB have investigated only 61 occurrences that get a publication_number, and 58 of which produced a report. So 738 of the 796 MAIB reports have no occurrence counterpart, and 9,005 occurrences have no adjoining report.

2. Parsed text

sentences

Every sentence of every report, in original reading order - 341,057 rows, 293,454 from MAIB documents and 47,603 from NTSB ones. The atomic unit of text; everything in the analysis layer traces back here. Sentences carry no jurisdiction of their own: join through document_id to split the corpora. Text is produced by a vision LLM reading a rendered image of each page, with deterministic passes applied on top - the stored text reflects that output, with the parent document's status indicating how much to trust it.

There is no sections table: a row with text_type = 'heading' is a section boundary, and a section's contents are the sentences whose sort_order falls between that heading and the next.

By text_type: 155,117 paragraph, 77,222 list_item, 47,648 heading, 32,532 frontmatter, 17,455 caption, 7,907 footnote, 3,176 table. frontmatter is cover pages, contents lists and boilerplate - exclude it from most analyses.

5. Embeddings

The pgvector layer behind SHIELD code suggestion: passages and SHIELD codes encoded under a registered model and compared by cosine distance. No API route exposes any of it - a separate worker container is the only writer of vectors, and the read path is the single function match_shield_codes, documented under passage_shield_codes.

Fully populated as delivered. embedding_models holds the single active encoder (BAAI/bge-large-en-v1.5, 1024 dimensions) and embedding_strategies the four assembly strategies. passage_embeddings carries a vector for every one of the 15,381 passages under that model, shield_code_embeddings all 452 vectors (113 codes × 4 strategies), and passage_embedding_queue is drained to 0 - no passage is awaiting or failing embedding.

Two properties are worth knowing before reading the tables:

  • Vectors are hash-addressed, not time-addressed. Every embedding row stores the SHA-256 of the exact text it was computed from, so a vector says what it embedded rather than when. To check whether one is current, compare its source_text_sha256 against the parent's - passages.source_text_sha256 on one side, text_sha256(shield_code_embedding_text(...)) on the other. Do not read updated_at as a freshness signal: a superseded vector sits in the table between a text change and the re-run that replaces it, so a hash mismatch means out of date, not corrupt. Writes are guarded (see § Database-enforced behaviour), which prevents a wrong vector, not a stale one.
  • Model generations coexist. model_id sits in every primary key here, so changing encoder is a new embedding_models row plus a re-run, never an in-place edit. A unique partial index allows only one row with is_active = true, and that is the row the queue and worker act on.

Database-enforced behaviour

Constraints participants should know about when writing to (or reasoning about) the data:

  • updated_at is trigger-maintained on every table.
  • verified_at / implemented_at are trigger-stamped from their boolean flags and cannot drift: application code writes only the boolean.
  • passage_sentences.sort_order is auto-assigned by trigger when inserted null.
  • Triggers validate that safety_issues.document_id and recommendations.document_id agree with the document derived from their passage_id - falling back to passages.document_id when the passage has no sentences attached yet - and that a narrative entity's mentions anchor only to sentences of the entity's own document.
  • passages.document_id is likewise trigger-validated (trg_validate_passage_document): it may not contradict the document derived from the passage's sentences, but a passage with no sentences yet may name its document freely. Deleting a document cascades to its passages.
  • documents.jurisdiction is CHECK-restricted to 'UK' or 'US' (or null); safety_issues.record_type to 'safety_issue' or 'safety_lesson', NOT NULL, defaulting to safety_issue; organisations.kind is a NOT NULL enum defaulting to company.
  • recommendations.reference_number is indexed but deliberately not unique - re-ingesting a document rewrites its records, so uniqueness would fight regeneration rather than protect anything.
  • tsvector columns (title_tsv, text_tsv, source_text_tsv, name_tsv, action_tsv) are generated columns and cannot be written directly.
  • Embedding rows are hash-addressed: trg_validate_passage_embedding and trg_validate_shield_code_embedding reject any vector whose source_text_sha256 disagrees with its parent's text at write time, or whose width disagrees with its model's dimensions. This stops a wrong vector being written; it does not delete an existing vector when its parent text later changes, so compare hashes rather than timestamps to tell whether one is current.
  • passage_embedding_queue is filled by trigger, never by application code: trg_enqueue_passage_embedding enqueues a passage whose source_text changed, and trg_clear_passage_embeddings deletes a passage's queue rows and vectors together when its text becomes null. Both fire on passages.source_text, so sentence-level edits reach them through the passage derivation stack.
  • embedding_models.dimensions is CHECK-restricted to 1024 (the width the vector columns are declared at) and provider to sentence_transformers or openai. A unique partial index (embedding_models_single_active_idx) permits only one row with is_active = true. embedding_models deleted out from under existing vectors is blocked by ON DELETE RESTRICT, as is an embedding_strategies row still named by a shield_code_embeddings row.
  • organisations.match_key and organisation_identifiers.match_key are generated (org_match_key(...)), stored, NOT NULL and UNIQUE - one company is one row and one spelling points at one organisation, whatever a caller intends.
  • source_id is UNIQUE on occurrences, vessels and affected_persons (and NOT NULL on occurrences / vessels) - the key MAIB spreadsheet ingestion upserts on (ON CONFLICT (source_id) DO UPDATE), touching only rows whose source_modified_at shows MAIB revised them.
  • documents.hash is UNIQUE (dedupes re-ingestion). The extraction lease is guarded by a CHECK: claim_expires_at may be set only when claim_started_at is.
  • taxonomy_terms enforces that a term's parent is in the same taxonomy (composite FK on (parent_id, taxonomy)).
  • documents.occurrence_matched_on is CHECK-restricted to publication_number or manual, and is required whenever documents.occurrence_id is set; document_particulars.loss_of_life must be null or ≥ 0; sentences.page_number must be null or ≥ 1.

Appendix A - SHIELD taxonomy

SHIELD is CHIRP's controlled taxonomy of human factors in maritime incidents: 113 factors in 24 categories under four layers. Each factor has a short code (e.g. PPC2), a title (e.g. "Fatigue") and a full definition; categories and layers carry their own codes and definitions too. The taxonomy is seeded reference data - the complete list is reproduced below and lives in the shield_layers, shield_code_categories and shield_codes tables.

SHIELD is presented as an iceberg: the visible acts at the tip, the preconditions that set them up below the waterline, the operational leadership decisions deeper still, and the organisation that shapes all of them at the base. For the model and its rationale, see the published paper: SHIELD Human Factors Taxonomy and Database for Learning from Aviation and Maritime Safety Occurrences (Safety, 2023).
