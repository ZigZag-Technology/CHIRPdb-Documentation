What we build, and what OpenAI provides

The finished Insight Engine is a free public chatbot that answers questions from CHIRP's verified incident reports. This page shows the parts behind it: the AI model we rent from OpenAI, the harness we build around it, the database it answers from, and how reports get into that database.

The one thing to take away

The OpenAI API is text in, text out. We send it one request and get one reply. It is stateless: it keeps nothing between requests, so it does not remember the conversation, search the web, draw charts or read our database. Everything that makes ChatGPT or Claude feel capable is a harness their makers built around the model, and for the Insight Engine we have to build that harness ourselves.

The four parts

Rented from OpenAI

The AI model

Reads text and writes text, and is stateless. Each request stands alone: anything it needs to know, including what was said earlier in the conversation, has to be sent again every time. Its reply is either an answer or a request for us to fetch something.

Built by us

The harness

Turns a stateless model into a chatbot. It handles memory, uploads, database searches, charts and tables, legislation look-ups, usage limits and cost caps. It also checks that every claim in an answer cites a verified report.

Built by us

CHIRPdb

The database the chatbot answers from. Every report is broken into sentences, recommendations, safety issues, people, vessels and places, indexed by meaning, with the original PDF kept. The public only ever sees what CHIRP staff have verified.

Built by us

Behind the scenes

The ingestion pipeline reads new reports. The review tool lets CHIRP staff approve what was extracted. The feature sweep adds new detail to every report when users' questions call for it. The first two already exist; Tranche 2 points them at ~15 more jurisdictions.

One question, start to finish

Take a seafarer who types: "Help me write a risk assessment for entering a cargo tank."

  1. They ask. The harness checks usage limits and screens for misuse. Any attached photo or draft document is held for this conversation only.
  2. The harness picks out features. "Enclosed space", "cargo tank", "tanker". Features the database already records can be searched straight away.
  3. One request goes to OpenAI. It contains instructions, the conversation so far, the question, any attachment, the reports found so far, and a list of things the AI may ask us to fetch.
  4. One reply comes back. Usually the first reply is something like "search for enclosed-space incidents on tankers", not an answer.
  5. The harness fetches it from CHIRPdb, adds the results to a fresh request and sends that. Steps 3 to 5 repeat until the reply is an answer.
  6. The harness checks and dresses the answer. Every claim must cite a verified report, or it isn't shown. Any chart or table is drawn by the harness from database figures, not by the AI.
  7. The seafarer gets a draft risk assessment built from real incidents, with each hazard linked to the report it came from.

One question can mean several OpenAI requests. Each one is billed, which is why the harness enforces a spending cap.

Getting faster with every question

Users will ask about things nobody thought to record. When a question depends on a feature the database doesn't hold yet, the harness starts a feature sweep. The sweep sends each report's text to the AI, one request per report, asks whether that feature applies, and stores the answer against the report.

Example. Someone asks how many groundings happened at night. "Time of day" isn't a recorded field, so the first answer takes a sweep across the corpus.

After the sweep, "at night" is a learned feature on every report. The next person to ask anything involving night-time gets an immediate answer from the database, with no sweep and far fewer AI calls.

Learned features are marked as AI-found until a reviewer confirms them, in keeping with the rule that AI proposes and humans verify. Answers that rely on them say so.
